Implementation Notes: Check Items through ItemService with per-User state

Design Decisions

  • ItemService.setItemChecked remains the domain operation for checked-state writes, receiving the active User ID from Home's active Member context and upserting only that User's item_checks row for the Item.
  • ItemService.listItems derives visible checked state from the latest item_checks.updated_at row for each Item, then exposes domain-shaped checked and checkedByUserId fields for Home to map.
  • Home's Active List data source keeps the UI-facing mapping from checkedByUserId to Member display name, leaving reusable Active List components independent of HouseholdStore and service factories.
  • Checked-state writes stay local-first: the service resolves after the local Household DB commit, and Home requests sync separately without making sync success part of the mutation result.

Deviations From Spec

  • Most issue #20 implementation code was already present from the issue #19 slice; this change hardens the missing issue-specific test coverage rather than rewriting the existing service boundary.

Tradeoffs Considered

  • Returning the updated Item from setItemChecked would make Home reload-free, but the current Active List UI already performs optimistic updates and reloads through its existing data source lifecycle, so the service keeps a narrow mutation result.
  • Putting sync inside ItemService would centralize propagation, but it would violate the documented local-first service boundary and make offline network failure look like a failed local Item action.
