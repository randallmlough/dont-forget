Implementation Notes: Load Home List through ListService

Design Decisions

  • Issue #18 is implemented as a narrow List metadata service slice: ListService owns List SQL and returns a domain-shaped List record, while the existing Active List data source continues to own Item SQL and sync behavior until the ItemService slice.
  • ListService binds the Household ID at construction and receives the List ID per getList call.
  • Missing and tombstoned Lists are treated the same by the service and surface as a not-found error to preserve the current Home load failure path.
  • ListService validates SQL rows with Zod before returning domain-shaped records, using shared SQL value helpers from db/utils.ts.
  • ListService does not accept an analytics dependency yet because getList is a metadata read; product analytics stay reserved for meaningful product outcomes such as Household Session loading or future List mutations.

Deviations From Spec

  • None yet.

Tradeoffs Considered

  • The Home Active List data source remained in lib/app/active-list-data-source.ts for this slice because moving it to screens/home/ then would have moved direct Item SQL and the temporary remote sync fallback into the screen layer before ItemService existed. Issue #21 later removed the legacy app data-access module and kept the data source under screens/home/.
  • The service depends on the executable subset of HouseholdStore because List metadata loading needs only SQL execution; the production Home path still passes the shared HouseholdStore instance opened by the Active List data source.
  • A shared asError helper was added under lib/errors.ts to avoid repeating local error normalization functions across logging boundaries.
