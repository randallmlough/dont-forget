Implementation Notes: Migrate Server Bootstrap Into Domain Server Services

Design Decisions

  • Issue #22 is implemented as a decomposition of the existing Household bootstrap coordinator. The API route remains a thin lazy-loading request handler, while User, Member, Household, and provisioning responsibilities move behind domain server services.
  • The bootstrap coordinator remains under lib/services/household/server/ because it returns a Household Session shaped response and composes multiple domain services for Home startup.
  • User, Member, and Household server services own their directory SQL directly. Household provisioning owns Turso Platform/database migration/default List infrastructure so the coordinator no longer mixes those concerns with session response assembly.

Deviations From Spec

  • None yet.

Tradeoffs Considered

  • Kept the existing public bootstrapUser export for the API route and tests instead of renaming the external entrypoint, so the route-level behavior stays stable while the internals move to domain service factories.
  • Generated IDs and timestamps now live inside the domain services and provisioning service rather than being injected through bootstrap dependencies. Tests assert observable ID shape and persisted behavior instead of exact generated IDs.
