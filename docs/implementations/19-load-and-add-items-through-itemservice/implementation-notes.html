Implementation Notes: Load and Add Items through ItemService

Design Decisions

  • ItemService will own Item listing and creation SQL through the injected HouseholdStore executable seam, binding Household ID at construction and receiving List/User/name operation inputs.
  • Home's Active List data source will move to screens/home/active-list-data-source.ts now that List and Item read/create SQL can be service-owned.
  • Item creation remains local-first: ItemService.addItem resolves after the local insert, while the Home data source requests sync separately after the service returns.
  • ItemService.addItem emits the typed item_added analytics event after local write success with Household, List, Item, and User IDs, intentionally excluding the Item name.
  • Checked-state mutation moved into ItemService as a small boundary cleanup so screens/home/active-list-data-source.ts can compose services without issuing direct Household SQL.
  • The temporary remote sync fallback moved under the Household service layer so the screen-owned data source does not import database clients directly.

  • None yet.

Tradeoffs Considered

  • Although issue #19 only names Item listing and creation, moving checked-state SQL at the same time avoids leaving a screen-level SQL exception immediately beside the new ItemService.
