Implementation Notes: Rename Active List Adapter Contract to Data Source

Design Decisions

  • Issue #17 is implemented as a behavior-preserving hard cut from Active List adapter terminology to data source terminology, with no old type, prop, factory, or module aliases kept in touched code.
  • The reusable Active List component continues to own the UI-facing data source contract and does not import HouseholdStore, Household Session, or domain service factories.
  • The Home startup path continues to compose a Household Session into the Active List data source before rendering ActiveList.Provider.
  • The renamed legacy data source factory remained under lib/app/active-list-data-source.ts for this slice because issues #18 through #21 separately migrated ListService/ItemService CRUD and removed legacy Home/List/Item app data-access modules. Issue #21 later moved the final data source to screens/home/active-list-data-source.ts.

Deviations From Spec

  • None yet.

Tradeoffs Considered

  • Moving the factory to screens/home/active-list-data-source.ts during this slice would have matched the final service-backed folder shape, but it would have moved direct SQL and HouseholdStore access into the screen layer before ListService and ItemService existed.
  • Keeping a compatibility wrapper for createHouseholdActiveListAdapter would reduce call-site churn, but issue #17 explicitly calls for no compatibility alias in touched code.
