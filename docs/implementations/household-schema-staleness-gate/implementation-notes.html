Implementation Notes: Household Schema Staleness Gate

Design Decisions

  • Root cause of post-migration no such column errors on existing accounts was load ordering, not replication: the Authenticated App Session published services before the Sync Coordinator's startup sync, so the Home List read a stale replica and its error state never recovered. See docs/adr/0013-household-schema-staleness-gate.md.
  • lib/services/household/household-schema.ts compares the local __drizzle_migrations max created_at with the bundled journal's max when (EXPECTED_HOUSEHOLD_SCHEMA_VERSION). createSessionDataServices awaits one full sync only when the replica is behind; a current replica adds a single local read to session open.
  • The gate runs only for sync-authorized stores; local-only stores (tests, unauthorized cached sessions) have nothing to pull.
  • screens/home/use-home-current-list.ts retries the List load when a sync reports synced while the List is in an error state. The subscription exists only during the error state, and retries are edge-triggered on status transitions, so a persistently failing load cannot hot-loop.
  • make worktree-db / make worktree-db-destroy (scripts/worktree-db.ts, scripts/worktree-db-destroy.ts) isolate parallel migration-bearing worktrees with a per-worktree directory DB; destroy refuses to touch databases not named df-local-wt-* and restores the .env.local lines it replaced.

Deviations From Spec

  • The discussion plan (docs/.local/discussions/db-migration-strategy-discussion-2026-06-09.md) chose client-applied bundled migrations with PRAGMA user_version signaling. The gating spike falsified both premises (pull applies remote DDL; Turso Cloud rejects remote user_version writes; pull clobbers local user_version), so the implementation pivoted to the staleness gate the spike supported.

Tradeoffs Considered

  • Awaiting a sync at session open adds latency only in the just-migrated case; the alternative (publish first, heal later) is exactly the race being fixed.
  • Offline-open with a stale replica proceeds on the previous schema rather than blocking the app; ADR-0003's backward-compatible migration policy covers it.

Spike Evidence

scripts/spike-local-ddl-sync.mts (run with APP_ENV=local pnpm tsx scripts/spike-local-ddl-sync.mts) against scratch DBs in the local Turso group, on @tursodatabase/sync 0.6.1 and 0.6.0 (the React Native package's version):

  • Remote ALTER TABLE + tracking row arrived at an existing replica in one pull(); schema and tracking rows travel together.
  • Restart simulation: reopening the stale replica and reading before pull() reproduced no such column; the same read succeeded after one pull().
  • Remote PRAGMA user_version = N rejected by Turso Cloud (SQL_PARSE_ERROR: SQL not allowed statement); locally-set user_version reset to the remote's value by pull().
  • Locally re-running DDL the remote already ran failed with duplicate column name.
  • Pushing local-only DDL plus rows to a not-yet-migrated remote silently applied the DDL remotely — push carries DDL; remote-first ordering remains the policy.
