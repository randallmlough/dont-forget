# /api/data write applicator lives in the db layer

PR #129 ("PR-A") added the PowerSync write endpoint `/api/data`: a generic, schema-agnostic CRUD applicator that turns a batch of PUT/PATCH/DELETE ops into upserts, patches, and tombstones against the Postgres source. It landed entirely inside `lib/api/data/` and held raw `pg` SQL there. That contradicted `docs/how-things-work/api-routes.md` ("`lib/api` is not a data-access layer. If an API handler needs ... DB access, call the appropriate service instead of adding SQL to the handler.").

The code knew it. `lib/api/data/handler.ts` carried a self-declared `PLACEMENT EXCEPTION` comment justifying the raw SQL as "a generic CRUD applicator with no natural domain-service home (analogous to the documented `app/api/bootstrap` exception)" and deferred the fix: "the doc reconciliation is PR-D's job." So the boundary doc forbade the shape, the code asserted a new undocumented exception to that doc, and the reconciliation was punted to a future slice. That is two sources of truth and a perpetuated exception — both things this repo avoids.

The applicator is not domain data access. A domain service returns domain-shaped records for one aggregate (a `List`, an `Item`) and owns the SQL for it. The `/api/data` applicator returns no domain records at all: it is a table-agnostic upsert/patch/tombstone engine driven by a wire contract (PUT/PATCH/DELETE on a synthetic `id`), enforcing transport invariants — last-writer-wins by `updated_at`, tombstone monotonicity, an `updated_at` clamp, per-table/per-column allow-lists, and per-row Membership authz. Dispersing it into the `list`/`item`/`member` services would scatter one transport contract across several domains and re-pose "where does this generic write live?" on every table.

[ADR-0014](0014-db-layer-owns-data-store-infrastructure.md) already answered the category question for the symmetric case: `HouseholdStore` was infrastructure that was "not a service," so ADR-0014 homed it in `db/` rather than under `lib/services/household/`. The `/api/data` applicator is the same category on the server side — data-store infrastructure, not a domain service — so it belongs in the db layer.

A lint rule forces the move to be complete. `tools/eslint-rules/no-services-imports-in-db.js` (the `no-services-imports-in-db` rule from ADR-0014) bars any non-test file under `db/**` from importing `@/lib/api` or `@/lib/services`, including `import type`. So once the SQL applicator moves into `db/`, the Zod batch contract, the `DataOp` type, and the `DataTransaction` interface it exchanges with the shim must move down with it; they cannot stay in `lib/api` and be imported by db code. The dependency arrow is strictly `lib/api -> db`, which ADR-0014 sanctions.

## Decision

We will relocate the entire `/api/data` write applicator into the db layer and leave `lib/api/data/handler.ts` a thin HTTP transport shim.

- `db/server/sync/applicator.ts` owns the pure `applyOp` core plus the contracts it exchanges with both sides: the Zod `opSchema`/`batchSchema`, the `DataOp` type, `StoredRowState`, the `DataTransaction` interface, and `DataClientError`. The core takes no `Request` and no `pg` handle; it runs against an injected `DataTransaction` (tests provide a fake, production wires the pg one).
- `db/server/sync/pg-transaction.ts` owns the raw `pg` SQL: `pgDataTransaction` (the `DataTransaction` implementation), `defaultWithTransaction` (one connection, `BEGIN`/`COMMIT`/`ROLLBACK`), and `PgQueryClient`. It is the only module that knows the pg wire shape.
- `db/server/sync/authenticate.ts` owns the production `defaultAuthenticate` (sub-only Clerk `verifyToken`, then resolve the internal `users.id` by `clerk_user_id`) and `DataAuthError`. Its `@/lib/server/auth`, `@clerk/backend`, and `@/lib/env` imports are dynamic and are cross-cutting `lib/` utilities, not the `lib/services`/`lib/api` layers the rule bars.
- `db/server/sync/index.ts` is the public surface the shim imports from, pointing the arrow `lib/api -> db`.
- `db/schema/postgres/sync-columns.ts` owns the column metadata: `WRITABLE_COLUMNS`, `HOUSEHOLD_RESOLUTION`, `DataTable`, and `isDataTable`. The old `lib/api/data/columns.ts` is deleted; nothing in `lib/api` re-declares this.
- `lib/api/data/handler.ts` is a ~107-line shim: authenticate -> `parseBatch` -> run the db-owned `applyOp` for each op inside one `defaultWithTransaction` -> map errors to status (`DataAuthError` -> 401, `DataClientError` -> its `status`, anything else -> 500). It imports everything down from `@/db/server/sync`. The `PLACEMENT EXCEPTION` comment is deleted.
- `WRITABLE_COLUMNS` is **derived** from the Drizzle schema via `getTableColumns`, not hand-listed, so the security allow-list cannot silently drift from the actual columns. `getTableColumns(...).name` yields the snake_case SQL column name, which is exactly what incoming `op.data` keys are. A per-table `EXCLUDE` set (empty today) names any column that must stay non-writable. A test in `db/schema/postgres/sync-columns.test.ts` pins the derived sets to the exact names and counts (`lists` 8, `items` 10, `item_checks` 5), so adding or removing a writable column is a deliberate edit to the `/api/data` security boundary, not an incidental schema change.
- `HOUSEHOLD_RESOLUTION` stays **explicit** (`lists` -> `row-household-id`, `items` -> `via-list`, `item_checks` -> `via-item`). It is a 3-row authz policy, not a mechanical projection of column names, so it is kept hand-written rather than derived.

Why `db/` and not `lib/services/<domain>`: domain services own domain-shaped data access and return domain records; `architecture.md`'s "SQL stays confined to domain services" governs *that* product data access. The `/api/data` applicator returns no domain records — it is a generic, table-agnostic write engine for the PowerSync transport. That is the data-store-infrastructure category ADR-0014 homes in `db/` (the `HouseholdStore` precedent), so the "SQL in domain services" rule is untouched and this applicator is correctly placed below it.

## Considered options

- **Keep the applicator in `lib/api/data/` with the self-declared exception (status quo).** Rejected: it contradicts `api-routes.md`, perpetuates an undocumented second exception, and defers reconciliation indefinitely. The repo keeps one source of truth.
- **Disperse the applicator into the `list`/`item`/`member` domain services.** Rejected: it is one transport contract, not per-domain behavior; splitting it scatters the LWW/tombstone/allow-list invariants and re-poses the placement question per table. It also returns no domain records, so it fails the "services return domain-shaped records" rule.
- **Move only the SQL to `db/` and leave the Zod contract and `DataOp`/`DataTransaction` types in `lib/api`.** Rejected: the db applicator imports those types, and `no-services-imports-in-db` forbids `db/ -> lib/api` even for `import type`. The contract must move down with the SQL.
- **Hand-maintain `WRITABLE_COLUMNS`.** Rejected: a hand list drifts from the schema; a forgotten column silently fails closed (rejected write) or, worse, a removed `EXCLUDE` silently opens a column. Deriving from the schema with a pinned-snapshot test makes drift a visible, deliberate edit.

## Consequences

- `api-routes.md`'s "`lib/api` is not a data-access layer" now holds literally for every route: no `lib/api` file contains data-store SQL. The `/api/data` placement exception is removed, not perpetuated. The doc is updated to say the write logic, batch contract, and SQL live in `db/server/sync` (this ADR); the `app/api/bootstrap` legacy exception is unaffected.
- This discharges the deferred "doc reconciliation" the old comment assigned to PR-D. PR-D is now scoped only to the remaining two-pool-per-request hardening (`defaultAuthenticate` and `defaultWithTransaction` each open and `end()` their own pool today).
- `db/server/sync/pg-transaction.ts` is the first module under `db/server` to issue raw `client.query` SQL; every other `db/server` module uses Drizzle or only builds a `Pool`. This is a deliberate, documented exception: the applicator is table-agnostic and conflict-strategy-specific (e.g. `item_checks` conflicts on `item_id` with an `updated_at` LWW guard), which is awkward to express through Drizzle's typed builder, so raw parameterized SQL is the honest tool. Columns are gated by the derived `WRITABLE_COLUMNS` allow-list and all values are parameterized.
- The schema-derived allow-list is allow-by-default minus `EXCLUDE`. A future server-managed column (e.g. a version/sequence stamp) would be client-writable the moment it is added to the schema unless it is also added to the table's `EXCLUDE` set. The pinned-snapshot test surfaces the new column on the next run, but the obligation is real and is documented in `sync-columns.ts`.
- Factual correction to the PR #129 review thread: the "empty-resolution authz gap" is already fail-closed. `assertAuthorized` throws `403` ("Could not resolve Household") when `householdsForOp` returns no Household, so an op that resolves to no Household is never authorized (`db/server/sync/applicator.ts`).
- The applicator preserves the [ADR-0015](0015-shared-per-item-check-with-attribution.md) `item_checks` invariants: one row per `item_id`, uncheck NULLs `checked_at`/`checked_by_user_id` rather than deleting, and concurrent checks merge last-writer-wins by `updated_at` (the upsert conflicts on `item_id`, not the synthetic `id`). ADR-0015's reference to the applicator living in `lib/api/data/` is updated to `db/server/sync`.
- This extends [ADR-0014](0014-db-layer-owns-data-store-infrastructure.md): the db layer owns data-store infrastructure on the server write path too, and `no-services-imports-in-db` keeps the `lib/api -> db` direction enforced.
