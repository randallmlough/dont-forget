# Household schema staleness gate at session open

After a Household schema migration fanned out to remote Household DBs (ADR-0003), existing devices kept failing with errors like `no such column` until the User signed out, because the local replica's schema only advances on the next successful `pull()`. An Issue-less spike (`scripts/spike-local-ddl-sync.mts`, results in `docs/implementations/household-schema-staleness-gate/`) proved the sync engine itself is not the problem: `@tursodatabase/sync` 0.6.x applies remote DDL to an existing replica on `pull()`, replicates the Drizzle `__drizzle_migrations` tracking rows together with that DDL in the same pull, and a single pull heals a stale replica. The bug was ordering inside the app: the Authenticated App Session published services before the Sync Coordinator's startup sync ran, the Home List load raced ahead of the first pull, failed against the stale schema, and nothing reloaded after sync — so the failure looked permanent across restarts.

We will keep the server as the only schema writer and gate session open on schema staleness instead: `createSessionDataServices` compares the local replica's `__drizzle_migrations` state against the migration journal the app build was compiled with (`db/migrations/household/meta/_journal.json`), and when the replica is behind it awaits one full sync before services are exposed. The Home List additionally retries automatically when a sync completes while the List is in an error state.

## Considered Options

- **Client-applied bundled migrations (Turso's registry pattern).** Rejected on spike evidence: re-running DDL locally that the remote already ran fails with `duplicate column`, and it is unnecessary because `pull()` already delivers the DDL. Two schema writers per Household DB would add conflict surface for no benefit.
- **`PRAGMA user_version` as the version signal.** Rejected on spike evidence: Turso Cloud rejects remote `PRAGMA user_version = N` writes (`SQL_PARSE_ERROR: SQL not allowed statement`) so the server cannot stamp it, and `pull()` clobbers a locally-set value back to the remote's. The Drizzle tracking table is the truthful signal instead — its rows and the DDL they describe arrive in the same pull, so locally it never describes a schema the replica does not have.
- **Re-bootstrap on mismatch (delete local DB, re-download).** Rejected: heavier than one pull, discards pending local writes unless pushed first, and the sync engine already heals in place.
- **Schema-tolerant service code only (the `PRAGMA table_info` pattern).** Rejected as the primary mechanism: it cannot cover writes against missing columns and taxes every service per migration. It remains the documented fallback for the residual case below.
- **Gate at session open on the tracking table (chosen).** Zero added latency when the replica is current (the common case — one local read), one awaited sync only when a migration actually landed, and no new schema writers.

## Consequences

- `lib/services/household/household-schema.ts` owns `EXPECTED_HOUSEHOLD_SCHEMA_VERSION` (the newest bundled journal `when`) and `ensureHouseholdSchemaReady`. `createSessionDataServices` runs it for sync-authorized stores before returning services; reads can no longer race the first pull after a migration.
- A replica that is still stale after the gate's sync (offline open, or the remote was not migrated yet) proceeds on the previous schema. This residual case keeps ADR-0003's rule alive: Household migrations must stay backward-compatible with the previous shipped app version (additive / expand-contract; renames and drops need a two-phase rollout). A local schema newer than the app build logs a warning and proceeds for the same reason.
- Operational ordering: migrate remote Household DBs (`make db-migrate`) before running app code built against the new schema. The spike showed pushing local writes that reference a column the remote lacks silently migrates the remote via pushed DDL — do not rely on that; it bypasses the fanout's `__drizzle_migrations` bookkeeping.
- The Home List subscribes to sync status while in an error state and retries on the next successful sync (`screens/home/use-home-current-list.ts`), so mid-session healing (for example connectivity returning) no longer requires a manual retry.
- Parallel development efforts that each carry a Household migration must not share the local environment's databases: Drizzle's migrator applies by latest `created_at`, so divergent migration sets from two branches either union onto shared DBs or get silently skipped. `make worktree-db` gives a worktree its own directory DB (and therefore its own Households) inside the existing local group; `make worktree-db-destroy` removes it and restores `.env.local`. Migration-free worktrees keep sharing the default environment safely.
- ADR-0003 and ADR-0009 are unchanged: WAL replication does propagate DDL to replicas, and the app still runs no bundled Household migrations. This ADR closes the gap those ADRs left implicit — *when* the replicated DDL arrives relative to the session's first read.
