# Product analytics goes through a typed abstraction with auto-synced identity

Product-event tracking in the RN app goes through `lib/analytics.ts` rather than calling `posthog.capture/identify/reset/screen` directly. The abstraction exposes four functions — `track`, `identify`, `reset`, `screen` — plus a `useAnalyticsIdentity()` hook. Event names and per-event property schemas are defined as a typed `EventMap` in `lib/analytics-events.ts`; `track` is parameterized over this map so both the event name and properties are checked at compile time. The PostHog adapter applies the same Bearer/JWT redaction the logger does (extracted into shared `lib/redact.ts`).

The canonical user identifier is **Clerk `user.id`**, not the user's email. `useAnalyticsIdentity()` runs once in `AuthGate` (inside `<ClerkLoaded>`) and auto-fires `posthog.identify(user.id, ...)` whenever Clerk's user changes, sending only non-personal creation metadata such as `created_at` as `$set_once`. Auth screens no longer call `identify` themselves; they just `track(...)` and `setActive(...)`. PostHog's anonymous-id aliasing merges pre-`setActive` events onto the now-identified person.

This complements [ADR-0004](./0004-pluggable-logger-abstraction.md): `logger.*` is for unbounded diagnostic data, `track(...)` is for the curated product-event vocabulary. Both abstractions sit on PostHog today; either can be swapped independently.

## Consequences

- **Schema drift becomes a compile error, not a dashboard mystery.** The previous direct `posthog.capture("user_signed_in_apple", ...)` / `posthog.capture("user_signed_in_google", ...)` / `posthog.capture("user_signed_in", { method: "email" })` pattern was already drifting — three event names for one concept, with `method` only sometimes populated. Collapsing onto `track("user_signed_in", { method })` with a typed enum forces consistency. Renaming a property or tightening an enum surfaces every call site that needs updating.
- **Identity is unified across events and logs.** Pre-abstraction, events were keyed by email (when identify was called at all — Google sign-in skipped it) and logs were keyed by Clerk `user.id`. The same human had two PostHog identities. Pinning everything to Clerk `user.id` makes events and logs cross-referenceable; email survives as a person property for UI search.
- **Apple-after-first-time is no longer broken.** Apple SSO returns `credential.email` only on first sign-in; the previous code called `posthog.identify(undefined, ...)` on every subsequent Apple sign-in. The auto-sync hook reads from Clerk, which always has `user.id`, regardless of which provider was used and how many times.
- **Auth screens shrink.** Each auth flow used to hand-roll its own identify call with slightly different `$set` / `$set_once` shapes. Now they just emit a tracked event. The "what traits go into PostHog?" question lives in one place.
- **Services and stores can inject analytics.** Service factories and store open configs that own product outcomes may accept typed analytics dependencies, scoped to the operations they actually need, and default to the app analytics helpers at the service/store boundary. This lets tests and non-app processes capture product events without mocking the singleton helpers.
- **Existing PostHog person records (keyed by email) are orphaned by this cutover.** This was an explicit choice: the project is pre-launch with test users only, and the alias-merge code (one-shot `posthog.alias` gated by AsyncStorage) was not worth the complexity for data that has no analytical value. If we re-do this for an app with production users, the migration is non-trivial.
- **Dashboards built on `user_signed_in_apple` / `user_signed_in_google` event names will go cold.** Dashboards that filter `user_signed_in` by `method` will keep working. Auto-generated dashboards from the integration wizard fall in the first category and are expected to be rebuilt or retired.
- **Adding an event is a 2-file change.** Edit `EventMap`, then call `track(...)`. Slight friction, deliberate — the question "is this really a new event?" gets asked at exactly the moment it should be asked. The escape valve is `logger.info(...)`, which has no schema requirement.
