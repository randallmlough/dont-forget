# Directory database on Postgres — single schema and concurrency strategy

The PowerSync migration replatforms Don't Forget from libsql/Turso to a single self-hosted Postgres fronted by PowerSync. PR-C1 re-points the **directory** database (Users, Households, Memberships, Invitations, Household Join Codes) from a libsql/Turso directory to that one Postgres, addressed by a single `DATABASE_URL`. There is a brief, intentional coexistence window: per-Household **product** data (Lists, Items, `item_checks`) stays on its per-Household Turso databases until the full cut-over, so during PR-C1 both engines run — Postgres for the directory, Turso for product data.

Before PR-C1 the repo carried two Drizzle schemas for the same six directory tables: `db/schema/directory.ts` (bigint epoch-millis; included `turso_db_name` and `provisioning_completed_at`) and `db/schema/postgres/directory.ts` (timestamptz; omitted those two columns). It also still carried the SQLite-era concurrency machinery the libsql directory needed. This ADR records how PR-C1 unifies the schema and re-establishes concurrency safety the Postgres-native way. It captures what the migration plan called "Decision 7."

## Decision

**1. One directory schema, bigint epoch-millis.** `db/schema/postgres/directory.ts` is the sole source of truth for the six directory tables; the duplicate `db/schema/directory.ts`, the `db/drizzle/directory.config.ts` config, and the `db/migrations/directory/` migration set were removed, and every importer now resolves the directory schema through the `@/db/schema/postgres` barrel. Directory timestamps stay **bigint epoch-millis** (`(extract(epoch from now()) * 1000)::bigint`), not `timestamptz`, because the service, test, client, and wire layers are all built on numeric epoch-millis (`z.number()`); switching to `timestamptz` would force a client wire-format change for no gain. (Correction, 2026-06-30: an earlier draft justified this by saying the directory "is not in the PowerSync publication" — that is inaccurate. `users`/`households`/`memberships` are in the `powersync` publication; during PR-C1 the client still read directory data through the `/api` bootstrap path, but PR-C2 wired the client onto PowerSync, so the directory is now client-synced. The resulting `bigint`-vs-ISO client representation was reconciled on 2026-07-03: the client schema declares the directory timestamps as integer epoch-millis — matching PowerSync's `bigint` serialization — and `src/client/session/powersync/schema-consistency.test.ts` mechanically enforces schema/stream/publication agreement.) The product tables (`lists`, `items`, `item_checks`) keep `timestamptz` because they are PowerSync-synced. The unified directory schema retains `turso_db_name` (NOT NULL UNIQUE) and `provisioning_completed_at` on `households` — still needed to address each Household's Turso database during coexistence. The on-disk Postgres migration was fresh-regenerated as a single `0000` (one clean migration, no additive ALTERs), and the hand-maintained PowerSync publication is re-added as `0001` (drizzle-kit does not emit `CREATE PUBLICATION`).

**2. SQLite-era machinery removed.** Postgres runs MVCC, so the libsql concurrency scaffolding is obsolete and was deleted: the `SQLITE_BUSY` busy-retry helper (Postgres does not raise it), the Household Join Code attempt throttle, and the per-Household lifecycle "locks" (`lifecycle-lock.ts`, whose `SELECT FOR UPDATE` substitute was a no-op `UPDATE` because SQLite has no row locks).

**3. Concurrency safety re-introduced the Postgres-native way.** Removing the lifecycle locks (Decision 2) reopened races on directory invariants that survive a single statement but not a concurrent pair. We restore per-Household serialization with a real Postgres row lock — `SELECT id FROM households WHERE id = $1 FOR UPDATE`, via `lockHouseholdRow(tx, householdId)` in `lib/services/shared/server/directory-transaction.ts` — taken at the start of the transaction body, before any policy reads. The lock is held until commit, so a second device's transaction queues behind the first and re-reads fresh committed state.

A command takes the lock when, and only when, it is a **server-side directory transaction that must preserve a cross-row invariant the database cannot enforce on its own.** Two shapes qualify, and the rule is the criterion — not the specific commands, which are only today's instances:

- **A multi-row invariant with no unique-index backstop, where the lock _is_ the only enforcement.** "Every Household keeps at least one Owner" (`removeMember`, `changeMemberRole`, `leaveHousehold` in the member service) and "at most one reusable pending Invitation per (Household, email)" (`createInvitation`, which serializes via its `findOrCreateInvitation` helper, in the invitation service) are each a read-decide-write over a _set_ of rows whose rule cannot be expressed as a unique index, so two concurrent transactions can each read stale state and commit a violation. Any future directory command of this shape (e.g. a transfer-ownership that must leave exactly one Owner, or a quota that caps active Members per Household) takes the lock for the same reason.
- **Deterministic ordering of competing lifecycle mutations on one conceptual resource, even where a unique index exists.** `disableJoinCode` and `regenerateJoinCode` serialize so disable-vs-regenerate ordering is well-defined and a `regenerate`-vs-`regenerate` race becomes a clean queue instead of a `23505` on the active-code partial unique index (`household_join_codes_active_household_unique`).

What does **not** earn a lock is **authorization freshness.** A command that reads "is the requester still an Owner / still a Member" before a single-row write is not maintaining a data invariant: whichever way it interleaves with a concurrent demotion or removal, the Household is left in a valid, reversible state. `renameHousehold` is exactly this — its only cross-row dependency is an is-Owner check, and its write is a single-row, last-writer-wins `households.name` update — so it intentionally keeps no lock. Treating authorization staleness as lock-worthy would not stop at rename: every membership-gated mutation reads the same kind of permission, so the rule would demand locking adding an Item, renaming a List, and checking an Item too. That is both unnecessary (no invariant is violated) and impossible — product mutations are not server-side directory transactions at all; they are client-authored and PowerSync-synced (last-writer-wins, with access enforced by the sync layer), with no transaction to hold a row lock in. Authorization in this system is request-time, and rename sits on that side of the line alongside the product mutations.

This supersedes the migration plan's blanket lock removal for the specific commands named above.

## Considered options

- **Keep both directory schemas (status quo).** Rejected: two definitions of the same six tables drift; the timestamptz variant had already lost `turso_db_name`/`provisioning_completed_at`. The repo keeps one source of truth.
- **Switch directory timestamps to `timestamptz`.** Rejected: the directory is not PowerSync-synced and the entire service/test/client/wire stack is numeric epoch-millis (`z.number()`); `timestamptz` adds no value server-side and breaks the client wire format.
- **Leave the lifecycle commands unserialized and rely on application reads.** Rejected: the last-Owner and duplicate-pending-Invitation invariants are multi-row with no unique-index backstop, so two concurrent transactions can each read stale state and commit a violation. A row lock is the minimal, native fix.
- **Add partial unique indexes to backstop these two invariants instead of a lock.** Rejected for now: "≥1 Owner per Household" is not expressible as a unique index, and a pending-Invitation partial unique index would change Invitation semantics; the row lock is the faithful, surgical replacement for the removed locks.

## Consequences

- The directory has one schema, one config, and one migration set. A second `drizzle-kit generate` against `db/drizzle/postgres.config.ts` is a clean no-op, confirming the regenerated snapshot/journal are consistent.
- The offline PGlite test suite applies `db/migrations/postgres` including `0001_powersync_publication.sql`. PGlite (embedded WASM Postgres) executes `CREATE PUBLICATION` successfully, so the harness applies the publication migration unchanged; no skip-filter is needed. Real-Postgres application via `make pg-migrate` is a separate operational step the offline suite does not exercise.
- The PGlite test harness serializes transactions on a single connection, so the row lock simply acquires and proceeds; existing "concurrent"/"race" tests still pass but now validate `23505` conflict handling against the partial unique indexes, not true DB-level interleaving (annotated in the join-code service test).
- Residual risks and revisit triggers:
  - **Join Code throttle removal.** The right revisit trigger is active-Household count / an abuse signal (a brute-force spray's hit probability is roughly `H / 2^40` for `H` active Households), **not** code length. Reintroduce throttling when that signal warrants it.
  - **Per-request `new Pool()` in the directory request path.** Intentionally deferred. Move to a module-level singleton before PR-C2 raises directory traffic; the exact shape depends on the hosting model.
  - **Index-backed invariants stay backstopped.** The Household Join Code and Membership uniqueness invariants keep their partial unique indexes (`household_join_codes_active_household_unique`, `memberships_active_unique`); the row lock only covers the two invariants that have no such backstop.
