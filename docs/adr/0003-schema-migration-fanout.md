# Schema migrations fan out across the directory DB and every Household DB

Because of the per-Household DB topology (ADR-0001), every schema change must be applied to **N+1 databases**: the directory DB plus one libSQL DB per Household. A migration runner iterates all Household DBs via the Turso platform API and applies pending migrations tracked per-DB in a `_migrations` table; new Households are provisioned by applying all current migrations to a fresh DB before returning a sync token. Schemas are defined in **Drizzle** and migration SQL is generated by **drizzle-kit**.

## Consequences

- Migration runs are not atomic across DBs. The runner applies migrations to each DB in sequence and exits non-zero if any DB fails — partial success is possible and must be handled by re-running.
- Migrations must be **backward-compatible** with the previous shipped app version, because Turso's WAL replication propagates DDL to device replicas immediately, while old app builds in the wild may still be running until App Store updates land. Add columns freely with `DEFAULT`s; renames and drops require a two-phase rollout (ship new column → ship app using it → wait for old apps to die → drop old column).
- The app does not run bundled Household schema migrations against synced local Household DBs. The server-migrated Turso Household DB remains the schema authority; app code must tolerate the previous local schema when opening offline before a sync can bring down newer DDL.
- The Household provisioning endpoint cannot return a sync token until *all* migrations are applied to the new DB. This puts a non-trivial latency floor on Household creation — acceptable for a deliberate user action, not for hot paths.
- SQLite's `ALTER TABLE` is restrictive (no type changes, no constraint changes on existing columns). Non-trivial schema changes require the table-rebuild dance (`CREATE new` → `INSERT … SELECT` → `DROP old` → `RENAME`) wrapped in a transaction.
- Household provisioning is not atomic across the directory DB and Turso's platform API. Directory `households` rows track when provisioning is complete so bootstrap can retry a pending Household instead of creating duplicates or returning a half-ready Household.
