# Single self-hosted Postgres synced to devices by self-hosted PowerSync

Don't Forget originally gave every Household its own replicated libSQL/Turso database, with a separate server-only directory database ([ADR-0001](0001-per-household-libsql-database.md)) synced to devices through the native Turso React Native package ([ADR-0009](0009-turso-react-native-for-native-household-sync.md)). That topology drove roughly a third of the codebase: a per-Household session resource lifecycle (open/lease/replace/close), a sync-coordinator stack, `HouseholdStore` plus a schema-staleness gate, server-side provisioning that fanned migrations out across every Household database ([ADR-0003](0003-schema-migration-fanout.md), [ADR-0013](0013-household-schema-staleness-gate.md)), and clients holding day-scale full-access Household tokens with no server-side write validation. ADR-0001 had rejected a single shared database only because Turso offered no row-level authorized partial sync — a vendor constraint, not a product one. A time-boxed spike (`plans/015-powersync-spike-report.md`) returned **GO-WITH-CAVEATS**: instant offline writes, sub-second propagation, server-authoritative instant revocation with automatic local purge, deterministic last-writer-wins by app-owned `updated_at`, and no client migrations because client tables are declarative views over synced data.

We will replatform onto a single self-hosted Postgres fronted by self-hosted PowerSync, as a clean cut-over (no dual-run, no flags, no coexistence window), and delete the Turso machinery outright.

## Decision

- **One Postgres holds everything.** A single self-hosted Postgres (`drizzle-orm/pg-core`, addressed by `DATABASE_URL`) holds both the directory (Users, Households, Memberships, Invitations, Household Join Codes) and product data (Lists, Items, `item_checks`). There are no per-Household databases. The directory is server-side only; the product tables (and, latently, some directory tables) are published to PowerSync.
- **PowerSync syncs by membership.** A self-hosted PowerSync service streams rows to a device scoped by the signed-in User's active Memberships, not by the active Household. Every Household a User belongs to is present in local SQLite, so **Household switching is local filtering** (re-point the `household_id` filter), not a per-Household fetch. This is designed for the MVP constraint of one User on one primary device; cross-device-same-user concerns are out of scope.
- **The client reads and writes through PowerSync natively.** `@powersync/op-sqlite` opens one local database over a **declarative** `AppSchema` (`lib/powersync/schema.ts`); there are **no client migrations**. Product services depend on a narrow `ProductDatabase` seam (`watch()` / `writeTransaction()` / `getAll` / `getOptional` / `execute`) rather than a SQL executor. Reads are reactive through `session.services.changes` (PowerSync's onChange) behind the engine-agnostic `useSessionQuery` hook (built in plan 014); connection state is surfaced read-only through `session.services.sync` (`getStatus` / `subscribe`). There is no sync coordinator and no `requestSync` — PowerSync streams continuously.
- **Writes go through a developer-owned `/api/data` endpoint.** The client connector's `uploadData` posts a batch of PUT/PATCH/DELETE ops to `app/api/data+api.ts`, a thin route that delegates to the `lib/api/data/handler.ts` shim, which runs the applicator in `db/server/sync`. Authentication is **sub-only Clerk `verifyToken` then a `clerk_user_id -> users.id` lookup** (not a Clerk Backend-API `getUser` round-trip). The applicator enforces Tier 1 (JWKS verify; per-row Household-membership authz via `list_id -> lists.household_id`, and `item_checks` via `item_id -> items -> lists`; per-table/column allow-listing; terminal-`4xx`-discard vs transient-`5xx`/network-retry) and Tier 2 (tombstone monotonicity; server-side `updated_at` clamp to `<= now()`). Its placement as db-layer infrastructure is [ADR-0016](0016-data-write-applicator-in-db-layer.md); the `item_checks` write invariants are [ADR-0015](0015-shared-per-item-check-with-attribution.md).
- **The PowerSync connection token is fetched directly from Clerk.** The connector's `fetchCredentials` calls Clerk `getToken({ template: "powersync" })` with no backend round-trip. The bootstrap route therefore returns **directory identity only** — it no longer returns any `householdDatabase` token block.
- **Household creation is one atomic transaction, with no starter List.** Creating a Household is a single Postgres transaction: a `households` row, the owner `memberships` row, and an initial join code. The two-phase Turso provisioning lifecycle (pending/complete, remote DB create + migrate + token mint + seed) is gone. **No starter List is seeded** ([Decision 6](../.local/discussions/powersync-migration.md)); a new Household lands in the existing empty-list state that prompts the User to create their first List. Auto-creating a User's first Household on sign-up is retained.
- **Directory concurrency and `item_checks` keep their own records.** Stripping the SQLite-era locks/throttle down to Postgres-native uniqueness plus a targeted row lock is [ADR-0017](0017-directory-database-on-postgres-single-schema-and-concurrency.md). Modeling `item_checks` as one shared attributed row per Item is [ADR-0015](0015-shared-per-item-check-with-attribution.md). This ADR does not re-derive them.
- **Current List selection stays local.** Per-`(User, Household)` selection remains a local AsyncStorage pointer layered over a watched query of the active Household's Lists, not synced Postgres state. Active **Household** selection is different — it is synced directory state (`users.active_household_id`). Sign-out clears local synced data via PowerSync `disconnectAndClear`.
- **Deployment.** One VPS runs Postgres on the private Docker network only (`DATABASE_URL`), the self-hosted PowerSync service (`EXPO_PUBLIC_POWERSYNC_URL`), and the API — including `/api/data` — reached at `EXPO_PUBLIC_API_BASE_URL`. The VPS/host/deploy specifics are owned by PR-E.

## Considered alternatives

- **Preserve the Turso-shaped seams as thin facades over PowerSync.** Rejected: it is faster and lower-risk, but the `HouseholdStore` SQL executor and the sync-coordinator facade would become single-use adapters the zero-tech-debt mandate flags for later removal. The genuinely engine-agnostic `useSessionQuery` seam is kept; the Turso-shaped seams under it are deleted.
- **A dual-write / coexistence parity window.** Rejected: the greenfield/no-users/no-fallbacks mandate removes any need for a live migration, and coexistence would add exactly the legacy-support complexity the project forbids. This is a clean cut-over.
- **Stay on Turso with a single shared database via its new partial sync.** Rejected: Turso partial sync is page-level lazy loading (a performance feature), not row-level authorized filtering, so it provides no tenant isolation — ADR-0001's privacy rejection of a shared Turso database still holds.
- **A different sync engine (Zero, ElectricSQL).** Rejected during the architecture audit: Zero 1.0 rejects writes while offline (offline Item writes are a hard product requirement); ElectricSQL is read-path sync only, leaving the write path hand-rolled.

## Consequences

- **Supersedes** [ADR-0001](0001-per-household-libsql-database.md), [ADR-0003](0003-schema-migration-fanout.md), [ADR-0009](0009-turso-react-native-for-native-household-sync.md), and [ADR-0013](0013-household-schema-staleness-gate.md). Their rejected-alternative reasoning (single-shared-DB privacy, op-sqlite) is the justification this ADR builds on and is retained as history.
- **Amends** [ADR-0002](0002-row-level-lww-with-split-checked-state.md) (transport), [ADR-0008](0008-environment-isolation.md) (environments), [ADR-0011](0011-domain-first-service-layer.md) (service layer), [ADR-0012](0012-authenticated-app-session-controller.md) (session controller), and [ADR-0014](0014-db-layer-owns-data-store-infrastructure.md) (db infrastructure). It does not supersede the newer decisions [ADR-0015](0015-shared-per-item-check-with-attribution.md)/[ADR-0016](0016-data-write-applicator-in-db-layer.md)/[ADR-0017](0017-directory-database-on-postgres-single-schema-and-concurrency.md), which document facets of this same migration.
- **Deleted machinery:** the sync-coordinator stack, `HouseholdStore` and its operation queue, the session cache/resource-manager/resource-lease lifecycle, Household provisioning, the schema-staleness gate, per-Household databases, and all Turso deps/configs/scripts. Roughly a third of the codebase's topology-driven complexity is removed.
- **Schema changes have three coordinated edit points** instead of a migration fan-out: a server Postgres migration (`db/migrations/postgres`), the declarative client `AppSchema`, and the PowerSync sync rules (`infra/powersync/sync-config.yaml`). The client runs no migrations.
- **Consciously deferred hardening** (server-authoritative timestamping, `/api/data` rate/payload/batch caps, join-code abuse protection, invitation-reuse index, leave-drain, offline cold-start restoration) is recorded in [`docs/tech-debt/powersync-deferred-hardening.md`](../tech-debt/powersync-deferred-hardening.md), not built here.
- **One known client-sync gap remains open:** the directory tables' synced timestamp representation (Postgres `bigint` epoch-millis vs the client schema's declared ISO text) is unreconciled and tracked in [`docs/tech-debt/powersync-directory-client-sync-representation.md`](../tech-debt/powersync-directory-client-sync-representation.md).
